# /release-check

Web サービス・モバイルアプリを一般公開する前の共通チェックリストと、対象 repo への適用フロー。ベースは [catnose さんの公開前チェックリスト](https://zenn.dev/catnose99/articles/547cbf57e5ad28)。

## 公開準備の開始ゲート

公開準備の最初に確認し、issue の先頭に置く。

- [ ] 正式名を決定する
  - 候補ごとに、多言語で不適切な意味にならないか、対応するドメインを取得できるか確認する
- [ ] 本番ドメインを取得する
- [ ] app ID / Bundle ID を確認する
  - 正式名が未決定の仮置きは `dev.nozomiishii.<repo 名>`。dance なら `dev.nozomiishii.dance`
  - `dev` は `nozomiishii.dev` 由来の固定 prefix で、開発環境を表す末尾 suffix ではない

ゲート未通過のときの規則:

- 全項目の調査と issue 本文の作成は続け、ゲート未通過と明記する
- ブランド、OAuth callback、メール送信ドメイン、公開 URL、本番 routing はゲート通過まで着手しない
  - 実装済みの機能が多いことを、名称とドメインを後回しにする理由にしない
- 仮 ID のままローカル build と検証は進めてよい
  - App Store Connect へ最初の build を upload した後は[変更できず](https://developer.apple.com/documentation/xcode/changing-the-bundle-identifier)、app record を削除しても再利用できない
  - upload 前に現在値をユーザーへ提示して確定する

## リリースまでの流れ

1. 公開する面と順序を決める
   - Web、ブラウザ拡張、iOS、Android、macOS を分け、各面の v1 範囲と公開条件を issue の先頭に書く
   - 同時公開が要件でなければ、後続ストアの未完了で先行する面を止めない
2. 開始ゲートを通す
   - 正式名、本番ドメイン、app ID / Bundle ID、価格と無料枠を確定する
3. 本番基盤を用意する
   - 環境を分け、DB migration、バックアップと復元、secret、外部サービス、監視、deploy と rollback を検証する
4. 法務文書、問い合わせ、ストア申告を実態に合わせる
   - プレースホルダを残さず、アプリ内と公開 URL の導線を確認する
5. release candidate を固定する
   - format、lint、型検査、unit、build、E2E、実機を通し、対象ブラウザとアクセシビリティを手動確認する
   - ストア提出物は同じ commit から作る
6. 段階公開する
   - preview または TestFlight で本番サービスを結線し、決済、メール、認証、エラー通知、外形監視を実データで確認してから公開する
7. 公開直後に監視する
   - 主要フロー、課金と解約、ログ、使用量と費用、問い合わせ導線を確認し、問題時に停止または rollback できる状態を保つ

各面に、前提、作業、受け入れ条件、公開後確認、rollback を持たせる。日付だけの段階名ではなく、観測できる通過条件を書く。

## 進め方

1. 対象 repo を調査して現在地を把握する
   - 実装済み・未実装を区別する
   - 既存のロードマップ文書・公開準備 issue があれば正本として尊重し、重複を作らない
2. 共通チェックリストの全項目を 済み / 未対応 / 対象外 に判定する
   - 法務・ITP・アクセシビリティ・外形監視のような、repo の調査だけでは痕跡が出ない観点も読み飛ばさず、全項目に判定を出す
3. 未対応項目を repo の現状に即して具体化し、issue 本文にする
   - 関連ファイルや設計 doc への参照を添え、repo 固有の項目も足す
   - 済み項目は「済み」として本文に残し、対象外項目は理由ごと末尾に残す
   - 実装の merge と本番確認を分ける。実サービスへの結線や smoke が未了なら、deploy または運用の issue に未対応として残す
4. 本文を提示して承認を得てから issue を作る

issue の規則:

- 既存 issue の前提が古ければ本文を現在地へ書き直す
  - 重複や置き換え済みの issue は、移行先へのリンクをコメントして閉じる。残タスクを閉じた issue に置かない
- ファイル・doc へのリンクは issue 上で解決される URL (`https://github.com/<owner>/<repo>/blob/main/...`) で書く
  - repo 相対パスは issue では壊れる
- 対象が外部 repo、または所有者を判定できない場合は、issue 作成より先に sibling の [oss SKILL.md](../oss/SKILL.md) を明示的に読み、その承認境界に従う
- 公開作業中に共通チェックリストの抜けに気づいたら回答で提案する
  - この skill の更新は、ユーザーが依頼した場合だけ dotfiles repo の `home/.agents/skills/release-check/SKILL.md` を変更する

## 法務

- [ ] 利用規約
  - 返金・日割り・解約条件を明記する
- [ ] プライバシーポリシー
  - エラートラッキング・メール送信・決済など、データの外部送信先をすべて列挙する
- [ ] 特定商取引法に基づく表記
  - 有料販売があるなら必須。決済代行 (Stripe 等) のアカウント審査でも要求される
- [ ] アカウント削除機能
  - GDPR と App Store 審査 (アカウント作成できるアプリは削除機能必須) の両方の要件
- [ ] 退会時にサブスクリプションを自動キャンセルする
- [ ] 電気通信事業の届出の要否
  - ユーザー間のメッセージ機能を提供するなら確認する
- [ ] 規約・ポリシーへの導線をアプリ内に設置する

文書のドラフトはテンプレートから作る:

- [利用規約テンプレート.md](references/利用規約テンプレート.md)
- [プライバシーポリシーテンプレート.md](references/プライバシーポリシーテンプレート.md)
- [特定商取引法に基づく表記テンプレート.md](references/特定商取引法に基づく表記テンプレート.md)
- 埋める前に [法務文書の埋め方.md](references/法務文書の埋め方.md) を読み、コードと運用の実態を確認する。推測で埋めると文書と実態がずれる

## サポートと運用

- [ ] お問い合わせ導線

  - 初回デプロイ後に一度実行して動作確認する

- [ ] アナリティクス

## 費用と支援制度

- [ ] 利用サービスの支援制度を確認する
  - repo とロードマップから、利用中・導入予定のクラウド / DB / 監視 / 認証 / AI / 開発ツールを洗い出す
  - sibling の [discount SKILL.md](../discount/SKILL.md) を明示的に読み、スタートアップ・個人開発者・OSS 向けクレジットや割引制度を公式ページで確認する
  - 対象条件、申請経路 (直接申請か提携 VC・アクセラレータ経由か)、付与額・割引率、有効期限、利用上限、対象外費用、有料プランへの自動移行を、公式 URL と確認日付きで残す
  - 期限付きクレジットの有効化時期は実際の利用開始に合わせ、公開前の早すぎる有効化を避ける

## メール送信

- [ ] SPF / DKIM / DMARC を送信ドメインの DNS に設定する
- [ ] 一斉送信するなら購読解除リンクと List-Unsubscribe ヘッダー
  - Gmail の一括送信者要件
- [ ] 送信処理の冪等性
  - webhook の at-least-once 配送やバッチ再実行で同じメールを二重送信しない

- [ ] セキュリティヘッダー

  - DB を正本にする実装パターン: [APIレート制限.md](references/APIレート制限.md)
- [ ] 更新・削除系 API の権限チェック棚卸し
- [ ] オープンリダイレクト対策
  - ログイン後の遷移先を検証する
- [ ] メールアドレス列挙防止

- [ ] 重要操作 (メールアドレス変更・退会等) の前に再認証を挟む

- [ ] 利用クラウドサービス (レジストラ・ホスティング・決済・メール) の 2FA 有効化

## 品質と複数環境

- [ ] iOS Safari 実機検証
  - メモリ上限・自動再生制約・IndexedDB クォータは実機でしか分からない
- [ ] iOS Safari の ITP 対策
  - 7日間訪問がないと localStorage / IndexedDB が削除されうる
  - 端末内保存が要のアプリは、PWA としてホーム画面に追加してもらうと対象外になる
- [ ] クロスブラウザ確認 (Chrome / Safari / Firefox) と OS 別フォント表示
- [ ] レスポンシブ確認
  - 長いユーザー入力で崩れないかも見る
- [ ] アクセシビリティ
  - img の alt、アイコンボタンの aria-label、スクリーンリーダー
  - freee アクセシビリティー・ガイドラインが実用的
- [ ] パフォーマンス

## ストア公開 (iOS / Android)

- [ ] Apple Developer Program 登録 (99 USD/年)、Google Play Console 登録 (25 USD 買い切り)
- [ ] [App Store Small Business Program](https://developer.apple.com/jp/app-store/small-business-program/) 申請
  - 前暦年と現暦年の全アプリ合計純収益が 100万 USD 以内なら、手数料が 30% から 15% になる
  - 自動適用ではなく申請が必要。持ち分 50% 以上の関連デベロッパアカウントも合算判定
  - 現暦年に超過するとその時点で標準手数料に戻る
- [ ] Google Play の 15% サービス手数料
  - 年間収益の最初の 100万 USD が対象。Play Console で適用条件と登録要否を確認する
- [ ] アプリ内課金の設計
  - ストア内のデジタル機能解放は原則 IAP 必須で、Web 用の決済 (Stripe 等) をそのまま流用できない
  - RevenueCat を採用するか明記し、未導入なら導入と検証をチェックリストに展開する。採用時は [RevenueCat.md](references/RevenueCat.md) を読む
  - 採用しない場合も、購入検証、通知、復元、複数ストアの契約状態をサーバーで一元化する
  - 日本はスマホ新法で外部課金の緩和が進行中。着手時に最新動向を確認する
- [ ] App Privacy (プライバシーラベル) と Google Play データセーフティの申告
- [ ] ストア掲載素材
  - アイコン・スクリーンショット・説明文
- [ ] 審査ガイドラインの確認
  - アカウント削除機能・年齢レーティング・トラッカー申告あたりが定番の指摘どころ
