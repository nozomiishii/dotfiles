# /doc

チャット返信以外の文章について、残す候補、置き場、書き方を決める。文章の推敲は yomiyasu skill に従う。

## いつ拾う

```text
候補
├─ 問題
│  ├─ 会話のコンテキストを使う → このセッション
│  ├─ 単独で進められる → 新しいタスク
│  └─ 調査や設計が必要 → issue
└─ 判断・知見 → 置き場
```

ユーザーが決めた時点で拾う。実行中の処理は止めず、次の切りのよい点で候補を提示する。セッションの最後まで先送りしない。

残すのは、好み、作業ルール、採用や見送りの判断など、ユーザーが意思決定したこと。一般知識など、AI エージェントに一度聞けば答えが返るものは残さず、その場で参照する。

振り返りを頼まれたときは、この節の条件に限らず、会話全体から問題と判断を拾う。

正本に既にある内容は、提示前に対象 repo と保存先の既存記録を確認し、候補から外す。

追加で見つけた候補は「確認」の表に足す。既に依頼または承認された対応は、対象 repo の既存手順で実行まで進める。新しいタスクは、ユーザーが選んだときだけ作る。

## 置き場

```text
判断・知見
├─ まだやっていない話（思いつき、保留、未着手の計画） → 対象 repo の issue
├─ なぜこうしたかの記録（設計を含む決着した判断） → 対象 repo の docs/decisions/ に ADR
├─ 今どうなっているかの事実（仕様、手順） → 対象 repo の docs/（実装の PR に同梱）
├─ 実装が終わるまでの設計書と計画 → 対象 repo の issue
├─ エージェントへの行動指針（呼称、進め方の好み、作業ルール） → AGENTS.md
└─ repo に限らない学び → nozomiishii/brain の知識ノート
```

```text
探す入口
├─ その repo の今 → AGENTS.md から docs/ へ
├─ 経緯 → issue 検索と ADR
└─ repo をまたぐ学び → brain vault
```

置き場はこのスキルの中で決め、ユーザーへの一問一答はしない。候補は「確認」の表で 1 回だけ出す。

エージェントへの行動指針は AGENTS.md に書く。全 repo 共通は dotfiles の home/AGENTS.md、repo 固有は対象 repo の AGENTS.md に置く。repo とその祖先に CLAUDE.md、.claude/CLAUDE.md、CLAUDE.local.md が 1 つでもあると AGENTS.md が読まれない。それらのファイルが必要に見えたら、ユーザーに判断を聞く。

brain の知識ノートは、分類、frontmatter、取り込みの作法を brain repo の指示ファイルに合わせる。

## 書き方

初見の読者が、会話を知らなくても意味を取れる文章にする。技術ブログとしてそのまま公開できる書き方にする。

- 文章の推敲は yomiyasu skill に従う。対象は、文の自然さ、主述の関係、比喩動詞、不要な装飾、読点、言い切りの強さ。
- yomiyasu が箇条書きを地の文にまとめる案を出しても、図と、1 つの話題の箇条書きは残す。
- yomiyasu が見出しを短くする案を出しても、節を見分ける語は省略せず残す。
- yomiyasu が「正本」を大げさな語として出しても、記録の用語として残す。判断、現状、担保、文脈も、元の文が主張を担っているときは残す。原文にない保証と出しても、元の文にその語があるときは残す。
- 太字、読点、比喩は yomiyasu skill に従う。仕様や手順の項目名を外すと意味が落ちるときは、ユーザーに判断を聞く。
- yomiyasu が一般知識を本文に足す案を出しても、詳細は公式ドキュメントかブログへのリンクにする。
- 指摘されたら、必要な分だけ伸ばす。
- 文章にはゴールを書く。
- 意思決定には、選択肢を比較し、採用や見送りを決めた理由を書く。
- 説明は IKEA の取扱説明書のように、図を中心にする。
- 図はゴールの直後に置く。
- 本文には、図だけでは伝わらない説明を最小限書く。
- 図の形式は、同じ repo の既存の文書に合わせる。前例が無ければ ASCII にする。ループや合流があって ASCII で線が引けないときは、Mermaid を使う。
- 書くのは、自分の環境、判断、記録など、AI が知り得ない事実。
- 一般知識や、コードと他の文書を読めば分かる詳細は、公式ドキュメントかブログへのリンクにする。
- 想定する読者にとって新しい事実を書く。
- 同じ内容の正本は 1 つにし、他はその正本へリンクする。
- 主語は、個人の名前ではなく、誰が読んでも通じる一般的なものにする。
- 見出しと箇条書きは、「設定ファイルを読み込んでからサービスを起動する」のように、言葉を省略せず最後まで書く。
- 1 つの箇条書きには 1 つの話題だけを書く。話題がもう 1 つあれば、別の箇条書きにする。
- 説明のための例に出す issue 番号、PR 番号、repo 名、ツール名は、架空の名前か一般名に置き換える。
- 仕様、手順、判断の記録では、正式名称と参照先を残す。
- 手順は箇条書きにする。番号が必要なときは、ユーザーに判断を聞く。
- リンクは、文の一部として読める語に付ける。記法を消しても文が成立するかで判別する。
  - `セットアップは README の[環境構築](URL)に従う` は成立する。
  - `[repo#123](URL) にセットアップ手順がある` は、識別子が残って読みが止まる。
- 文中の語に埋められないリンクは、脚注にする。番号や識別子はリンクテキストにしない。
  - `この構成は別の repo で検証済み[^verify-pr]` と書き、定義は文末にまとめる。
  - 脚注名は連番ではなく、内容の分かる固有名にする。並び替えても壊れない。
- 表やリストで項目そのものがリンクなら、項目をそのままリンクにする。
- 成果物には、その文書だけで完結する情報を書く。session URL や会話の出自は、公開したときに会話全文が露出しうる。載せる必要が出たら、ユーザーに判断を聞く。
- ルールは禁止で終わらせず、代わりにすることを書く。代わりが無いときは、ユーザーに判断を聞く。

## 種類ごとの差分

共通の書き方に、文書の種類ごとの条件を足す。

### README

- 日本語版 README.ja.md と英語版 README.md は、同じ構成を保つ。新しい項目は両方に追加する。
- 内容が食い違うときは、日本語版を正とする。

### SKILL.md と routine の prompt

- ゴール、境界、出力の条件を書く。手順やコマンドを足す必要が出たら、ユーザーに判断を聞く。

### コード内コメント

- 会話でユーザーから質問が出た項目を書く。

### ADR の書式

対象 repo に ADR の書き方を定めた文書があれば、そちらに従う。無ければ次の書式を使う。

```markdown
---
status: accepted
date: 2026-01-01
---

# 決めたことを一文で書いたタイトル

## 背景と課題

## 検討した選択肢

## 決定

## 結果
```

- `検討した選択肢` は、論点が 1 つなら箇条書きにする。複数あるときは、論点ごとの小見出しに分け、それぞれ「選択肢 / 評価」の 2 列表にする。
- 選択肢がコードのときは、概要でよいので、表の前に選択肢ごとのコード例を置く。表のセルには収まらない。
- 却下した案も `検討した選択肢` に残す。後から、なぜこれを選んだかを追えるようにするため。
- `決定` が長くなるときは、論点に対応する小見出しで分ける。
- `結果` は `良くなったこと`、`引き受けたコスト`、`保留した論点` の 3 つの小見出しに分ける。該当が無いときも見出しを残し、`なし` と書く。コストや保留が無いことも、判断の記録になる。
- 差し替えたときは `status: superseded by [後継の ADR](<後継のファイル名.md>)` にする。理由は本文の冒頭に引用ブロックで書く。

## 確認

会話から残す候補を列挙し、判定結果を表で 1 回だけ提示する。候補には番号を振り、「番号で指定してください」と添える。

| # | 内容 | 置き場 | アクション |
| --- | ---- | ------ | ---------- |

承認されたものから実行する。「2 と 4 だけ」のような番号での取捨選択と、「これは issue でなく ADR」のような修正指示は、反映してから実行する。issue の作成と PR は、ユーザーの承認を得てから実行する。

保存と PR の前に、新規の文書とまとまった量の追記は subagent にレビューを依頼する。1 行から 2 行の追記や、語句の修正は、レビューを省いて保存する。

- 渡すものは、書いた文章と、このスキルの「書き方」。
- 頼むことは、違反の指摘と、削れる箇所の提示。内容の追加が必要に見えたら、ユーザーに判断を聞く。
- 指摘を反映してから保存する。反映しなかったものは、ユーザーに伝える。
