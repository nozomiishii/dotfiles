# /doc

記録の置き場を判定し、保存まで実行する。置き場判定の正本はこのスキル。

保存までの段取り (branch・worktree・PR・重複確認) はこのスキルでは定めない。対象 repo の指示ファイルと既存ファイルの形式に合わせて、その場で判断する。

## 文章ガイドライン

書く文章すべてに共通。markdown もコード内コメントも、他のスキルの作業中に書くものも含む。

- 読み手は未来の自分と AI エージェント。文章の完成度より、鮮度と見つけやすさを優先する
- 書く・編集する前に[エンジニア特有の言い回しに染まらないための言葉遣いメモ](https://github.com/nozomiishii/brain/blob/main/brain/main/%E3%82%A8%E3%83%B3%E3%82%B8%E3%83%8B%E3%82%A2%E7%89%B9%E6%9C%89%E3%81%AE%E8%A8%80%E3%81%84%E5%9B%9E%E3%81%97%E3%81%AB%E6%9F%93%E3%81%BE%E3%82%89%E3%81%AA%E3%81%84%E3%81%9F%E3%82%81%E3%81%AE%E8%A8%80%E8%91%89%E9%81%A3%E3%81%84%E3%83%A1%E3%83%A2.md)を読み、避けたい表現を使わない
- 書くのは自分の環境・判断・記録など、AI が知り得ない事実だけ。一般知識も、コードや他の文書を読めば分かることも書かない
- コード内コメントは、会話でユーザーから質問が出た項目にだけ書く
- 要点だけ書く。背景・根拠・調査結果は docs に分けてリンクで指す
- 同じ内容を 2 箇所に書かない。正本を 1 つ決めて、他はそこへリンクする
- 新鮮で少量を保つ。古くなった記述は残さず消す
- 短くわかりやすい日本語で foolproof に書く。指摘されたら、必要な分だけ伸ばす
- 並び替え・追加削除に弱いため、手順番号は書かない
- 接続表現はなるべく省き、論理が飛ぶ所だけ明示する
- 太字は使わない。強調は見出し・箇条書きなど構造で示す
- 順序のある手順は箇条書きにする。読点でつないだ 1 文にしない
- 分岐・ループ・合流があるものは図にする。順序が一直線のものを図にしない
- 図にした内容は文から削る。同じことを文と図で二度言わない
- 図の形式は同じ repo の既存 docs に合わせる。前例が無ければ ASCII にする。
  ループや合流があって ASCII で線が引けないときは Mermaid を使う
- 丸括弧で補足する場合は、文や構造で示せないか考慮に入れる
- リンクは文の一部として読める語に付ける。記法を消しても文が成立するかで判る
  - `セットアップは README の[環境構築](URL)に従う` は成立する
  - `[repo#123](URL) にセットアップ手順がある` は識別子が残って読みが止まる
- 文中の語に埋められないときは脚注にする。番号や識別子をリンクテキストにしない
  - `この構成は別の repo で検証済み[^verify-pr]` と書き、定義は文末にまとめる
  - 脚注名は連番でなく内容の分かる固有名にする。並び替えても壊れない
- 表やリストで項目そのものがリンクなら、そのままリンクにする
- 例は文書を単体で読む人に通じるものにする。実在の issue 番号・PR 番号・repo 名・ツール名は読む人が知らないので、架空の名前か一般名に置き換える
- session URL や会話の出自情報を成果物に書かない。public 化した瞬間に会話全文が露出しうる
- 急ぎの依頼や「作法の確認は飛ばしていい」という言葉があっても、このガイドラインを省略しない。読み手は未来の自分なので、依頼者の今の急ぎは省略の理由にならない。直した上で変更点を報告し、戻すかは依頼者が決める

書き方のルールを新しく決めたら、その場でこのガイドラインに足す。決めた本人の記憶にだけ残すと、次の文書で同じ議論からやり直すことになる。

## 保存前のレビュー

書いた本人は自分の文章を削れない。長い作業の途中で書いたものほど、ガイドラインから離れる。保存・PR の前に subagent へレビューさせる。

- 渡すもの: 書いた文章と、上の文章ガイドライン
- 頼むこと: 違反の指摘と削れる箇所の提示。内容の追加は頼まない
- 指摘を反映してから保存する。反映しなかったものはユーザーに伝える

## README

- 日本語版 README.ja.md と英語版 README.md は同じ構成を保つ。新しい項目は両方に追加する
- 内容が食い違う場合は日本語版を正とする

## 判定フロー

内容ごとに次で判定する。判定はこのスキルの内部ロジックで行い、ユーザーへの一問一答はしない。

- まだやってない話 (思いつき・保留・未着手の計画) → 対象 repo の issue
- 未着手の実装の design doc → 対象 repo の issue
- 着手中の実装の design doc → 対象 repo の `docs/` (実装 PR で育てる)
- なぜこうしたかの記録 (決着した判断) → 対象 repo の `docs/decisions/` に ADR
- 今どうなってるかの事実 (仕様・手順) → 対象 repo の `docs/` (実装 PR に同梱)
- AI エージェントへの行動指針・フィードバック (呼称・進め方の好み・作業ルール) → AGENTS.md (全 repo 共通は `dotfiles/home/AGENTS.md`、repo 固有は対象 repo の `AGENTS.md`)。Claude Code に読ませる repo では `CLAUDE.md` から AGENTS.md を参照できる構成が必須
- repo に限らない学び → nozomiishii/brain の知識ノート。分類・frontmatter・取り込みの作法は brain repo の指示ファイルに従う

design doc の置き場は着手で切り替わる。着手したら issue の内容を `docs/` のファイルへ移し、実装 PR で実装と一緒に育てる。issue には移した先のリンクだけ残し、実装 PR で close する (正本は 1 つ)。

探すときの入口は 3 つ: repo のことは AGENTS.md から docs/ へ、経緯は issue 検索と ADR、横断は brain vault。

## ADR の書式

対象 repo に ADR の書き方を定めた文書があれば、そちらに従う。無ければ次を使う。

frontmatter は `status` と `date`。セクションは 4 つで、この順に置く。

```markdown
---
status: accepted
date: 2026-01-01
---

# 決めたことを一文で書いたタイトル

## 背景と課題

## 検討した選択肢

## 決定

## 結果
```

- `検討した選択肢` は、論点が 1 つなら箇条書きにする。複数あるときは論点ごとの小見出しに分け、それぞれ「選択肢 / 評価」の 2 列表にする
- `決定` が長くなるときは、論点に対応する小見出しで分ける
- `結果` は `良くなったこと` / `引き受けたコスト` / `保留した論点` の 3 つの小見出しに分ける。該当が無いときも見出しを残して `なし` と書く。コストや保留が無いことも判断の記録になる
- 却下した案を `検討した選択肢` に残す。後から「なぜこれを選んだか」を追えるようにするため
- 差し替えたときは `status: superseded by [後継の ADR](<後継のファイル名.md>)` にする。理由は本文の冒頭に引用ブロックで書く

## 候補の列挙と一括確認

会話から残す候補を列挙し、判定結果を表で 1 回だけ提示する。候補には番号を振り、「番号で指定してください」と添える。

| # | 内容 | 置き場 | アクション |
| --- | ---- | ------ | ---------- |

承認で実行する。「2 と 4 だけ」のような番号での取捨選択、修正指示 (「これは issue でなく ADR」等) があれば反映して実行する。issue 作成・PR は外向き操作なので、承認前に実行しない。
