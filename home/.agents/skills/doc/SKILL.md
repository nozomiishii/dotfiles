# /doc

チャット返信以外の文章について、残す候補、置き場、出力の条件、承認の境界を定める。

## いつ拾う

- ユーザーが意思決定した時点（好み、作業ルール、採用や見送りの判断）で拾う。一般知識などその場で引けるものは残さない。
- 実行中の処理は止めず、次の区切りのよいところで提示する。セッションの最後まで先送りしない。
- 振り返りを頼まれたときは、会話全体から問題と判断を拾う。
- 提示前に既存の正本を確認し、既にある内容は候補から外す。

## 置き場

置き場はこのスキルの中で決め、ユーザーへ一問一答しない。

- 未着手の話（思いつき、保留）、実装が終わるまでの設計書と計画 → 対象 repo の issue
- なぜこうしたかの判断記録 → 対象 repo の `docs/decisions/` に ADR
- 今どうなっているかの事実（仕様、手順） → 対象 repo の `docs/`（実装の PR に同梱。実装完了時に issue から残す仕様を移す）
- エージェントへの行動指針 → `AGENTS.md`（全 repo 共通は dotfiles の `home/AGENTS.md`、repo 固有は対象 repo の `AGENTS.md`。repo や上位ディレクトリに `CLAUDE.md`、`.claude/CLAUDE.md`、`CLAUDE.local.md` があると `AGENTS.md` が読まれないため、書き先についてユーザーに判断を聞く）
- repo に限らない学び → `nozomiishii/brain` の知識ノート（分類や書式は brain repo の指示に従う）

## 出力の条件

- 初見の読者が会話を知らなくても意味を取れる文章にする。session URL や会話の出自は書かず、必要な背景は本文に書く。出自を残す必要があると思えたらユーザーに判断を聞く。
- ゴールを書き、図で伝わる構造は図を中心にして本文は最小限にする。意思決定では選択肢を比較し、採用と見送りの理由を残す。
- 同じ内容の正本は 1 つに保ち、一般知識や他文書で分かる詳細はリンクにする。
- ルールは禁止で終わらせず、代わりにすることを書く。代わりが無ければユーザーに判断を聞く。
- 例示に使う番号や名前は架空または一般名にし、仕様・手順・判断記録では正式名称と参照先を残す。
- 日本語のまとまった文章（新規文書、まとまった追記や書き換え、PR・issue 本文）は、保存や作成の前に `yomiyasu` スキルで推敲し、推敲後の本文だけを成果物に使う（完了報告欄は混ぜない）。1〜2 行の追記、語句の修正、コード内コメント、英語の文章は省く。

### 種類ごとの条件

- README: `README.ja.md` と `README.md` を両方置くときは同じ構成を保ち、食い違うときは日本語版を正とする。
- SKILL.md・routine の prompt: ゴール、境界、出力の条件を書く。手順やコマンドを足す必要が出たらユーザーに判断を聞く。
- コード内コメント: 会話でユーザーから質問が出た項目を書く。
- ADR: 対象 repo に既存書式があれば従い、無ければ frontmatter（`status`, `date`）と 4 見出し（`背景と課題`、`検討した選択肢`、`決定`、`結果`）にする。却下した案も残す。差し替え時は `status: superseded by <後継 ADR>` として理由を冒頭に書く。

## 承認

- 会話から新しく拾った残す候補に番号を振り、判定結果（`#`、`内容`、`置き場`、`アクション`）を表で 1 回だけ提示し、「番号で指定してください」と添える。
- 番号での取捨選択や置き場の修正指示を反映してから実行する。既に依頼または承認された対応はそのまま実行し、未承認の issue と PR の作成はユーザーの承認を得てから実行する。
