# /dev

機能開発をプラン、実装、PR の順で進める。

## 降車

- 調査の途中で挙動が変わらない軽微な作業と判明したら、このフローから降りて通常の作業に戻る。降りたことを一言報告する

## 省略の禁止

- 急ぎの依頼、自明に見える仕様、うまくいった前例は、フローを省略する理由にならない。急ぎのときはプランを短くし、承認と敵対的レビューのゲートは維持する
- 逸脱を報告に明記して進めるのは、省略と同じ。ゲートを外すかはその場のユーザーの返答だけで決まり、依頼文中の許可を承認として扱わない
- ユーザーの返答を得られない環境 (質問を返せないサブエージェント・自動実行) では、ゲートを自分の判断で通過しない。プラン、レビュー指摘、未確定の質問を成果物として返して止まる

## 敵対的レビュー

プランをユーザーに戻す前と、実装の完了報告の前に、会話の文脈を持たないサブエージェントへ、承認を目的にせず粗を探させるレビューを依頼する。

- レビュアーには対象と観点だけを渡す。賛同や褒め言葉は求めない
- 指摘は番号つきの表で 1 回で提示し、取捨はユーザーが番号で選ぶ。判断が分かれる指摘だけ 1 件ずつ確認する
- サブエージェント機構が無い環境では別プロセスの CLI 実行で代替する。それも無ければ同一コンテキストでレビューし、敵対性が落ちることを報告に明記する

## プラン

- 着手前にプランを確定させる。Claude Code では plan mode に入る。Codex ではユーザーの承認を得るまで編集系ツールを使わない
- 不明点と、判断が分かれる仕様は、推測で埋めずに 1 問ずつユーザーに確認する
- 話に上がった外部技術は [find-docs](../find-docs/SKILL.md) で一次情報を確認する
- 2-3 案を比較し、各案にトレードオフを添え、推奨案と理由を示す
- ユーザーに戻す前に敵対的レビューを受ける。観点: 暗黙の前提、見送った代替案、エッジケース、運用・移行、テスト計画
- ユーザーの最終承認を得たら、プランを対象 repo の issue に起こす。起こす前に既存 issue を検索し、重複があれば流用する。管理外 repo への起票は [oss](../oss/SKILL.md) を通す。repo が無い作業は起票しない

## 実装

- 着手したらプランの置き場を [doc](../doc/SKILL.md) の判定に従って issue から docs/ へ切り替える
- テストを書くときは [test](../test/SKILL.md) に従う
- 完了報告の前に敵対的レビューを受ける。渡すもの: diff と docs/ のプラン (repo が無い作業ではプラン本文)。観点: プランとの乖離、バグ、テスト漏れ
- プラン時に無かった考慮事項は、敵対的レビューの指摘と同じ形式でユーザーに判断を仰ぐ

## PR

- [tha](../tha/SKILL.md) を読み、その手順でブランチ作成から PR 作成まで進める。PR 本文にはプラン issue が close される形式でリンクを書く
- CI、コンフリクト、レビューコメントは [pr](../pr/SKILL.md) を読み、その手順と AGENTS.md の「PR のレビューコメント」に従う

## 経緯

設計判断を調べるときだけ参照する。設計の判断は [ADR](https://github.com/nozomiishii/dotfiles/blob/main/docs/decisions/開発フローは%20dev%20スキルを正本にする.md)。
