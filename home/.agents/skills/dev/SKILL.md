# /dev

機能開発をプラン、実装、PR の順で進める。

## 対象外だとわかったとき

- 調べていくうちに、挙動の変わらない軽微な作業だとわかったら、このフローから降りて普通の進め方に戻る。降りたことは一言伝える

## フローを飛ばさない

- 急ぎの依頼でも、仕様が自明に見えても、前に同じやり方でうまくいっていても、フローを飛ばす理由にはならない。急ぎのときはプランを短くして、承認と敵対的レビューだけは必ず通す
- 「フローから外れます」と断って進めるのも、飛ばしたことに変わりはない。飛ばしてよいかは、その場でユーザーが返事をしたときだけ決められる。依頼文に「飛ばしていい」と書いてあっても、承認としては扱わない
- 返事をもらえないサブエージェントや自動実行など、ユーザーに質問できない環境では、自分の判断で先に進まない。プラン、レビューの指摘、決めきれなかった質問を成果物として返して止まる

## 敵対的レビュー

プランをユーザーに見せる前と、実装の完了を報告する前に、この会話の文脈を知らないサブエージェントにレビューを頼む。通すためではなく、問題を見つけるために頼む。

- レビュアーには対象と観点だけを渡す。賛成や褒め言葉は求めない
- 指摘を見せる前に、対象のプランや diff の該当箇所をユーザーが読める状態にする
- 指摘は置き場を 3 つに分ける。レビュー結果そのものは見せない
  - 採用した指摘はプランに反映する。チャットには反映した件数だけ書く
  - 見送った指摘はプランの末尾に理由と一緒に残す
  - ユーザーの判断が要る指摘だけをチャットに出す。書き方は AGENTS.md の「問題・発見が複数あるとき」に従う。「N / 全件数」の全件数は判断が要る指摘の数。選択肢があるときはトレードオフと推奨を添える
- 判断に必要な説明は、選択肢とトレードオフも含めて表にしない。番号で採否を求めない
- 1 回の質問ツール呼び出しに判断事項を複数件積まない。ツールが 1 問ずつ順に表示しても、質問どうしが独立でも、急ぎでも、まとめてよい理由にならない
- 質問文や選択肢の説明で、ユーザーがまだ見ていないファイル・用語・決まりを初出させない
- サブエージェントを使えない環境では、別プロセスの CLI 実行で代わりにする。それもできなければ同じ会話の中でレビューして、レビューの独立性が落ちることを報告に書く

## プラン

- 実装を始める前にプランを固める。plan mode には入らない。ユーザーが承認するまで編集系のツールを使わない
- わからない点や、決め方が分かれる仕様は、推測で埋めずに 1 問ずつユーザーに聞く
- 話に上がった外部技術は [find-docs](../find-docs/SKILL.md) で一次情報を確認する
- 2-3 案を比較し、各案にトレードオフを添えて、推奨する案と理由を示す
- ユーザーに見せる前に敵対的レビューを受ける。観点は、暗黙の前提、見送った代替案、エッジケース、運用と移行、テスト計画
- ユーザーの最終承認をもらったら、プランを対象 repo の issue にする。作る前に既存の issue を検索して、重複があればそちらを使う。管理外の repo に issue を作るときは [oss](../oss/SKILL.md) に従う。repo が無い作業では issue を作らない

## 実装

- 実装を始めたら、[doc](../doc/SKILL.md) の判定に従ってプランを issue から docs/ へ移す
- テストを書くときは [test](../test/SKILL.md) に従う
- 完了を報告する前に敵対的レビューを受ける。渡すのは diff と docs/ のプラン。repo が無い作業ではプランの本文を渡す。観点は、プランとのずれ、バグ、テストの漏れ
- プランのときに無かった考慮事項が出てきたら、敵対的レビューの指摘と同じ形式でユーザーに判断してもらう

## PR

- [tha](../tha/SKILL.md) を読んで、その手順でブランチ作成から PR 作成まで進める。PR 本文には、マージでプラン issue が close される形式のリンクを書く
- CI、コンフリクト、レビューコメントは [pr](../pr/SKILL.md) を読んで、その手順と AGENTS.md の「PR のレビューコメント」に従う

## 経緯

設計判断を調べるときだけ参照する。[開発フローを dev スキルに一本化した経緯](https://github.com/nozomiishii/dotfiles/blob/main/docs/decisions/開発フローは%20dev%20スキルを正本にする.md)と、[plan mode に入らない理由](https://github.com/nozomiishii/dotfiles/blob/main/docs/decisions/dev%20のプランは%20plan%20mode%20に入らず進める.md)は ADR にある。
