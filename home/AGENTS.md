# Global Guidelines

## コミュニケーション
- 返信は200〜300字で答え切る。詳細は求められたときだけ展開する。
- 長い文章の代わりに、図解・表・コードサンプルなど視覚的な解説を積極的に使う。
- 質問は1つずつする。
- ユーザーからの質問がある場合、ユーザーが理解や納得できるまで次の話題を提案せず深く掘り下げる。
- 推測で返信しない。実装と公式ドキュメントを確認してから答える。
- 参照先は必ずリンクで示す。
- 「プラン A」のようなラベルで物事を呼ばない。読み手が頭の中で変換せずに済む、内容の分かる言葉で名指しする。一覧提示時の一時的な番号振りは可。

## 禁止操作
- PR merge
- tofu apply
- GitHub review thread の Resolve

## 設計
- 新機能や修正の前に、plan mode で計画を質問しながら仕様を確定させる。
- 2-3 案を比較し、各案にトレードオフと推奨理由を添える。

## 実装
- 外部のバグや依存の制約でワークアラウンドを入れる時は、/watch スキルを使う。
- MCPツールが利用できる場合、CLIよりMCPツールを使う。
- 外部サービスの自動化は、UI 操作より先にエンドポイントを探す。ネットワークログや DevTools で内部 API を特定し、API 経由で操作する。

## Agents設定
- 必ずclaude code、codexどちらでも同じ挙動になるように作る。

## ユーザープロフィール

ユーザー本人や開発環境の情報が必要なときは `~/Code/nozomiishii/brain/brain/PROFILE.md` を参照する。

## 外部リポジトリ
- 管理外 (自分と所属 Organization 以外) のリポジトリへの書き込みは /oss スキルを使用する

## 静的解析ルールの抑制禁止
- lint・型検査・セキュリティスキャナのルール抑制は禁止。まずコードを直す。
  - どうしても必要なときは相談し、承認なしに抑制しない。自律判断の例外はない。

## デバッグ
- 3 回修正して同じ失敗が出たら、設計を疑いユーザーに返す。

## コード内コメントと PR / issue 本文
- 要点だけ書く。背景・根拠・調査結果は docs に分けてリンクで指す。

## コミットと PR
- 指定がなければ、PR 本文は日本語で書く。
- 明示的な指定なしに Draft PR を作らない。
- 指定がなければ、PR タイトルは、commitlintに従う。
- PR に依頼と無関係な変更を混ぜない。
- merge手順が発生する場合、GitHub Stacked PRを使う。
