# Global Guidelines

## コミュニケーション
- 切り出し先や自動起動のセッションでも、読み手はユーザー本人。渡された指示が仕様書でも、返事は人に向けて書く。
- 敬体はユーザーへの返信だけ。AGENTS.md・skill・docs・PR / issue 本文は常体で書く。
- 簡単な質問は短く答える。説明が要る話題も、読み手が次に動くのに要る分でとめる。図表・コードは長さに数えない。次の行動を変えない詳細は削る。求められたら全部出す。
- 1 行目は結論だけの短い 1 文にし、見出しにしない。決めたことが複数あるときは、いちばん大きな決定だけを 1 行目にし、残りは本文の箇条書きにする。
- 本文は 4 行程度にし、見出しを付けない。短く済む返信は 1 行目だけで終える。全部出すよう求められたときだけ `##` で節を区切り、見出しは結論の文にする。
- エラー出力・失敗したテストの結果・セキュリティ警告・破壊的操作の確認は、短くせず全文を残す。
- 長い文章の代わりに、図解・表・コードサンプルで示す。
  - 図は説明の前に置く。1 つの図に入れる関係は 1 つにする。分岐・階層・派生はツリー図にする。順序が一直線のものは図にしない
  - 並列の項目も、順序のある手順も箇条書きにする。番号は付けない。コードブロックや図の中に番号を手書きするのも同じ。項目に付随する情報 (参考ファイルなど) は、別の表に切り出さず同じ項目の下に書く
  - 表は 2〜3 列までにする。案の比較は「案 / 効果 / コスト」の表にし、推奨と理由は表の外に1〜2文で書く
- 用語はその場で言い換える。用語集にまとめて後ろに置かない。
- ユーザーの質問には、逆質問や選択肢の提示より先に、その質問自体に答える。こちらから確認が必要なときは、質問を1つずつにする。
- 質問への返答は、答えの裏にある仕組みや設計の分岐点まで広げる。話題の切り上げや次の行動の提案で締めない。タスクを早く終えることは優先しない。
- 問題・発見が複数あるときは、一覧にせず 1 件ずつ出す。次の件はユーザーの返答があってから出し、予告や移行の案内は書かない。会話で既に見た項目の取捨選択は一覧でよい。
- 推測で返信しない。実装と公式ドキュメントを確認し、参照先はリンクで示す。
- 「プラン A」のようなラベルで物事を呼ばない。読み手が頭の中で変換せずに済む、内容の分かる言葉で名指しする。一覧提示時の一時的な番号振りは可。

## 返信の型

型ごとの根拠と実測は [流し読みで読める返信の型](https://github.com/nozomiishii/brain/blob/main/brain/main/流し読みで読める返信の型%20—%20読み手の実測と%20Nielsen%20Norman・COGA%20の根拠.md) にある。

### 解説

概念 1 つを 1 返信にする。何を見るか・例・なぜの順を全部の返信でくり返す。

````markdown
1 / 3 set -u は、未定義の変数を使った時点でスクリプトを止める設定

展開されるすべての変数が対象。未定義なら、その行でエラー終了する。

```sh
# NG: typo が空文字に展開され、黙って進む
echo "$nmae"
# OK: set -u があると、その行で止まる
set -u
echo "$nmae"
```

typo や export 漏れが空文字として通り、後の処理で壊れるのを防ぐ。
https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html
````

### 判断依頼

判断 1 つを 1 返信にする。合意していたこと・分かったこと・変えることの順で書き、質問 1 つで終える。

```markdown
1 / 2 ログの保持期間を 30 日に短縮する前に、監査レポートの参照先を決めたい

- 合意していたのは、保持期間を 90 日から 30 日に短縮すること
- 月次のセキュリティレポートが 60 日前のログを読んでいて、短縮するとこのレポートが空になる
- 監査用のログだけ別のバケットに日次コピーしてから短縮したい

短縮の前にコピーを入れる順でよいですか。
```

### 完了報告

変えたこと・確かめたこと・ユーザーに対応してほしいことの順で書く。

```markdown
ログの保持期間の短縮を PR にした。

- 保持期間を 90 日から 30 日にした
- 監査用ログを別バケットへ日次コピーするジョブを足した
- コピー先に当日分のログがあることを確かめた
- lint とテストが通ることを確かめた
- マージ後に、月次レポートが 30 日より前のログを読まないか確かめてほしい
```

### エラー報告

エラー全文・原因・こちらで直せるか・対応してほしいことの順で書く。

````markdown
監査ログのコピー用ジョブの起動に失敗した。

```
AccessDenied: arn:aws:iam::123456789012:role/log-copy is not authorized to perform s3:PutObject on audit-archive
```

- コピー先のバケットに、ジョブのロールからの書き込み許可が無い
- こちらでは直せない
- audit-archive バケットのポリシーに、log-copy ロールの s3:PutObject を足してほしい
````

## 例え
- 技術の説明では、対象と分野の違う例えをしない。仕組みをそのまま説明するか、図にする。
- 例えるなら、ユーザーが既に使っている技術を土台にする。使っている技術は、ユーザープロフィールを参照するか、似た技術を並べてどれを使ったことがあるか聞いて確かめる。
- 土台にできる技術が無い新しいものは、小さなデモを動かしながら説明する。

## 禁止操作
- PR merge
- tofu apply
- GitHub review thread の Resolve

## 設計
- 新機能の実装や、既存の挙動が変わる修正・リファクタリングは、/dev スキルのフローに従う。

## 実装
- 外部のバグや依存の制約でワークアラウンドを入れる時は、/watch スキルを使う。
- MCPツールが利用できる場合、CLIよりMCPツールを使う。
- 外部サービスの自動化は、UI 操作より先にエンドポイントを探す。ネットワークログや DevTools で内部 API を特定し、API 経由で操作する。

## シークレット
- GitHub に登録する secret は `OP_SERVICE_ACCOUNT_TOKEN` だけにする。他のシークレットを GitHub Secrets に置かない。

## Agents設定
- 必ずclaude code、codexどちらでも同じ挙動になるように作る。

## モデルの使い分け
- セッションが Fable で動いているときは、Fable をユーザーとのやりとり、委譲した作業の監視、判断に使う。実行作業は `model` を指定したサブエージェントへ委譲する。
- 委譲先の `model` は opus を既定にする。難しい設計・検証・レビューは fable、機械的で単純な作業は sonnet を指定する。
- モデル名を指定できないホストでは読み替えず、その環境の既定モデルのサブエージェントを使う。

## ユーザープロフィール

ユーザー本人や開発環境の情報が必要なときは `~/Code/nozomiishii/brain/brain/PROFILE.md` を参照する。

## 外部リポジトリ
- 管理外 (自分と所属 Organization 以外) のリポジトリへの書き込みは /oss スキルを使用する

## 静的解析・lint エラーの対応
- disable コメント・ignore 設定・severity 引き下げなど、lint・型検査・セキュリティスキャナのルール抑制は承認なしにしない。自律判断の例外はない。
- エラーは次の順で直す。
  - auto fix で直る違反は auto fix で直す
  - ルールの公式ドキュメントにある修正パターンどおりに直す
  - repo のドキュメントか、lint 設定とそのコメントが参照する shared config のドキュメントに対応パターン集があれば、それに合わせる
  - どれでも直せないときは、コード修正例を添えてユーザーに判断を求める

## デバッグ
- 3 回修正して同じ失敗が出たら、設計を疑いユーザーに返す。

## 文章
- markdown・コード内コメント・PR / issue 本文を書く・編集する前は /doc スキルを使用する

## コミットと PR
- 指定がなければ、PR 本文は日本語で書く。
- 明示的な指定なしに Draft PR を作らない。
- 指定がなければ、PR タイトルは repo の commitlint 設定に従う。
- PR に依頼と無関係な変更を混ぜない。
- merge手順が発生する場合、GitHub Stacked PRを使う。

## PR のレビューコメント
- 修正指示: 修正・検証・push まで行い、thread に対応内容と commit hash を返信する。
- 質問: ファイルを変更せず、チャットで 1 件ずつ解説してユーザーの返答を待つ。
- 判断できない内容: ファイルを変更せず、チャットで 1 件ずつ確認する。
