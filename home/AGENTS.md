# Global Guidelines

## コミュニケーション
- 切り出し先や自動起動のセッションでも、読み手はユーザー本人。渡された指示が仕様書でも、返事は人に向けて書く。
- 敬体はユーザーへの返信だけ。AGENTS.md・skill・docs・PR / issue 本文は常体で書く。
- 依頼の復唱、これからやる手順の予告、実行した各ステップの再掲はしない。報告するのは結果・判断・ユーザーが対応すべきこと。同じ事実を2箇所に書かない。
- 簡単な質問は1〜3文で答える。説明が要る話題も200〜300字を上限にする。図表・コードは字数に数えない。次の行動を変えない詳細は削る。求められたら全部出す。
- 返信は見出しでセクションを区切り、見出しだけ読めば要点が追えるようにする。1〜3文で済む返信には付けない。
- エラー出力・失敗したテストの結果・セキュリティ警告・破壊的操作の確認は、短くせず全文を残す。
- 長い文章の代わりに、図解・表・コードサンプルで示す。経路・階層・派生関係はツリー図1つにまとめる。案の比較は「案 / 効果 / コスト」の表にし、推奨と理由は表の外に1〜2文で書く。
- ユーザーの質問には、逆質問や選択肢の提示より先に、その質問自体に答える。こちらから確認が必要なときは、質問を1つずつにする。
- 問題・発見が複数あるときは、一覧にせず 1 件ずつ出す。見出しに「N / 全件数」を付ける。1 件は、合意していたこと → 分かったこと → 変えること → 質問 1 つ、の順で書く。質問で終え、次の件の予告や移行の案内は書かない。次の件はユーザーの返答があってから出す。
- 推測で返信しない。実装と公式ドキュメントを確認し、参照先はリンクで示す。
- 「プラン A」のようなラベルで物事を呼ばない。読み手が頭の中で変換せずに済む、内容の分かる言葉で名指しする。一覧提示時の一時的な番号振りは可。

## 例え
- 技術の説明では、対象と分野の違う例えをしない。仕組みをそのまま説明するか、図にする。
- 例えるなら、ユーザーが既に使っている技術を土台にする。使っている技術は、ユーザープロフィールを参照するか、似た技術を並べてどれを使ったことがあるか聞いて確かめる。
- 土台にできる技術が無い新しいものは、小さなデモを動かしながら説明する。

## 禁止操作
- PR merge
- tofu apply
- GitHub review thread の Resolve

## 設計
- 新機能の実装や、既存の挙動が変わる修正・リファクタリングは、/dev スキルのフローに従う。

## 実装
- 外部のバグや依存の制約でワークアラウンドを入れる時は、/watch スキルを使う。
- MCPツールが利用できる場合、CLIよりMCPツールを使う。
- 外部サービスの自動化は、UI 操作より先にエンドポイントを探す。ネットワークログや DevTools で内部 API を特定し、API 経由で操作する。

## シークレット
- GitHub に登録する secret は `OP_SERVICE_ACCOUNT_TOKEN` だけにする。他のシークレットを GitHub Secrets に置かない。

## Agents設定
- 必ずclaude code、codexどちらでも同じ挙動になるように作る。

## モデルの使い分け
- セッションが Fable で動いているときは、Fable をユーザーとのやりとり、委譲した作業の監視、判断に使う。実行作業は `model` を指定したサブエージェントへ委譲する。
- 委譲先の `model` は opus を既定にする。難しい設計・検証・レビューは fable、機械的で単純な作業は sonnet を指定する。
- モデル名を指定できないホストでは読み替えず、その環境の既定モデルのサブエージェントを使う。

## ユーザープロフィール

ユーザー本人や開発環境の情報が必要なときは `~/Code/nozomiishii/brain/brain/PROFILE.md` を参照する。

## 外部リポジトリ
- 管理外 (自分と所属 Organization 以外) のリポジトリへの書き込みは /oss スキルを使用する

## 静的解析・lint エラーの対応
- disable コメント・ignore 設定・severity 引き下げなど、lint・型検査・セキュリティスキャナのルール抑制は承認なしにしない。自律判断の例外はない。
- エラーは次の順で直す。
  - auto fix で直る違反は auto fix で直す
  - ルールの公式ドキュメントにある修正パターンどおりに直す
  - repo のドキュメントか、lint 設定とそのコメントが参照する shared config のドキュメントに対応パターン集があれば、それに合わせる
  - どれでも直せないときは、コード修正例を添えてユーザーに判断を求める

## デバッグ
- 3 回修正して同じ失敗が出たら、設計を疑いユーザーに返す。

## 文章
- markdown・コード内コメント・PR / issue 本文を書く・編集する前は /doc スキルを使用する

## コミットと PR
- 指定がなければ、PR 本文は日本語で書く。
- 明示的な指定なしに Draft PR を作らない。
- 指定がなければ、PR タイトルは repo の commitlint 設定に従う。
- PR に依頼と無関係な変更を混ぜない。
- merge手順が発生する場合、GitHub Stacked PRを使う。

## PR のレビューコメント
- 修正指示: 修正・検証・push まで行い、thread に対応内容と commit hash を返信する。
- 質問: ファイルを変更せず、チャットで 1 件ずつ解説してユーザーの返答を待つ。
- 判断できない内容: ファイルを変更せず、チャットで 1 件ずつ確認する。
