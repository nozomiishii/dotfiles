# Global Guidelines

## コミュニケーション
- 質問は1つずつする。1ターンで意思決定を求める論点も1つ。論点をA/Bに分けて並べるのも複数質問として扱う。往復が増えるのは構わない。文脈から汲める確認は質問にしない。
- ユーザーの返信に質問が含まれていたら、回答してターンを終える。自分の回答で懸念が解消したと見なさず、次の作業はユーザーの指示を待つ。ツール実行を挟むターンの途中テキストは表示されないことがあるため、回答は必ずターン最後のメッセージに置く。
- 推測で返信は禁止。実装と公式ドキュメントを必ず確認する。
- grep や検索のヒット件数をそのまま事実として報告しない。該当行を開き、意図したものにマッチしているか確認してから報告する。
- lint ルール・設定コメント・根拠を求められた技術判断には、公式ドキュメントの URL を添える。
- 返答でGitHubのIssueやPRに言及する時は、必ずリンクにする。
- 手動でブラウザを操作する手順を案内する時は、必ず URL を添える。
- foo/bar/hoge/fuga のようなダミー名で例示しない。会話に即した実物名で示す。
- 複数の案を並べるときは、記号か番号を振り、各案に違いがパッと分かる最小限の例 (差分・図・出力イメージ) を添える。違いが文章だけで明らかなときは省く。
- 大量候補の確認は、内容を開けるリンクと選択UIを用意し、手入力を求めない。確認作業の継続が了承済みなら、各バッチの反映・検証後は「続き」を待たず次のバッチを提示する。
- ユーザーの入力には音声入力の誤変換が混ざる。続けて送り直された文は最新を意図として扱い、表記は文脈で補正する。

## 実装
- セッション開始ディレクトリ以外のリポジトリの変更は、新しいセッション (デスクトップは spawn_task、CLI は claude --bg) に切り出すのが基本。会話の流れ上、同一セッションで続ける場合は /wt スキルでワークツリーを切ってから作業する。
- .envrc のある repo では、その env に依存するコマンドを `direnv exec . <コマンド>` で実行する。非対話シェルでは direnv が自動発火しないため、env 不足で失敗したコマンドもこれで再実行する。
- 依頼のスコープを超える新しい概念・関数・抽象化を持ち込まない。既存の型・関数・命名を優先して使う。
- 外部のバグや依存の制約でワークアラウンド・一時対応をコードに入れる時は、/watch スキルで解消条件を expiring TODO か追跡 Issue に接続する。急ぎの依頼でも省略しない。
- 公式ドキュメントに無いやり方 (ライブラリ内部実装への依存、monkey patch、生成物の書き換え) でしか実装できないときは、手を止めてユーザーに判断を仰ぐ。技術構成の乗り換えも選択肢に出す。
- 情報の正本は1つにし、新しく二重管理になる構成を提案しない。
- 実装を変更したら、PR 本文・README・コメントも同じ内容に揃える。
- 実装コメントは控えめにする。コードを読めばわかる内容を書かない。
- 外部サービスの操作を自動化するときは、UI 操作より先にエンドポイントを探す。ネットワークログや DevTools で内部 API を特定し、API 経由で操作する。

## cloud セッション

Claude Code on the web など、ローカルの clone や gh が無いリモートセッションでの読み替え。

- `~/Code/<owner>/<repo>` 配下のパスが無い場合、セッションに既にある clone を探して再利用する。無ければパスから `<owner>/<repo>` を導出して add_repo し、clone 先をそのパスの読み替えとして以降の手順を行う。
- add_repo の実行は、承認プロンプトへのユーザーの承認をもって同意とする。承認を得られない場合はその repo の作業を中断して報告し、一時ディレクトリなど代替の置き場へ進まない。
- subagent からは add_repo の承認を得られない。repo は親セッションで揃えてから dispatch する。
- gh が無い場合、GitHub 操作は GitHub MCP の同等ツールに読み替え、gh コマンドの引数をそのままパラメータに写す。gh が省略時に default branch へ解決する base などは、対象 repo の実際の default branch を指定する。

## dotfiles の実体パス
`~/.claude/` 配下の設定はシンボリックリンクで、実体は `~/Code/nozomiishii/dotfiles/home/` 配下にある。編集は実体パスで行う。

- `~/.claude/CLAUDE.md` → `dotfiles/home/AGENTS.md`
- `~/.claude/skills/` → `dotfiles/home/.agents/skills/`

## 外部リポジトリ
- 外部リポジトリを変更する操作は /oss スキルを経由する。経由せず実行しない。
- 外部か判断がつかない場合は外部として扱う。

## 静的解析ルールの抑制禁止
- lint・型検査・セキュリティスキャナのルール抑制は禁止。まずコードを直す。
  - off / warn / disable / ignore / suppress、手段を問わず対象。
  - どうしても必要なときは相談し、承認なしに抑制しない。自律判断の例外はない。

## コミットと PR
- プロジェクトで指定がない場合、PR本文は日本語で書く。
- commit message と PR タイトルは、書く前に repo の規約を読んで従う。commitlint の設定 (type の enum) と、PR タイトルを検証する workflow (subject のパターン) の両方を見る。
- PR は指定がなければ通常の PR として作成する。Draft PR はユーザーが明示した場合だけ作成する。
- PR に依頼と無関係な変更を混ぜない。
- レビュー指摘は実装する前にコードベースで検証する。間違った指摘には技術的根拠をつけて押し返す。複数の指摘がある場合、不明点を全て確認してから着手する。
- レビューコメントへの対応はプッシュで終わらせず、必ず元コメントに返信する。対応した場合はどう対応したかとコミットの URL、対応しなかった場合は議論の内容と対応しない旨を返信する。

## デバッグ
- fix を試す前に原因を調査する。エラーの再現、最近の変更確認、コンポーネント境界でのログ追加を先行する。
- 仮説は 1 つずつ検証する。
- 3 回修正して同じ失敗が出たら、設計を疑いユーザーに返す。

## 設計の探索
- 新機能や大きな変更の前に plan mode で 2-3 案を比較する。各案にトレードオフと推奨理由を添える。
- scope が複数のサブシステムにまたがる場合は分割して個別に進める。

## 完了の主張
- テスト・build・lint の実行結果を確認せずに「直りました」「完了です」と言わない。
- commit や PR 作成の前に該当する検証コマンドを実行する。

## 検索
- GitHub IssueはClosedやduplicatedになっている場合、Openしているissueまで特定し提案する。
