# routine が壊した issue 本文の修復は GitHub Actions に任せる

## 背景と課題

brain の cloud routine が毎朝この repo に日報 issue を作る。本文が改行の代わりにリテラルの `\n` を含む1行文字列で投稿されることがあり、表示が壊れる。

routine の prompt には tmpfile を `--body-file` で渡す指示と、作成後に行数を検証して壊れていたら edit し直す手順が既にある。壊れた issue の多くは作成の約1分後に routine 自身が修復 edit しており、修復が実行されなかった issue は壊れたまま残る。

## 検討した選択肢

- routine の prompt をさらに強化する — 既に明示的な指示と検証手順があって失敗した。すり抜けが残る
- issue 作成用スクリプトを用意して routine に使わせる — 作成経路は決定的になるが、スクリプトを使うか自体が prompt 遵守に依存する
- GitHub Actions で壊れた本文を検出して修復する — LLM に依存せず決定的。routine が増えても効く。誤検出しないよう判定条件が要る

## 決定

GitHub Actions で修復する。

- issues の opened と edited で発火し、workflow_dispatch で issue 番号を指定した手動修復もできる
- 修復するのは author が repo owner で、本文が1行に潰れてリテラルの `\n` を含む issue だけ。第三者の issue は書き換えない
- edit の直前に本文を取り直して判定し直す。取り直してから edit するまでの短い窓は残るが、routine 自身の修復と競合してもどちらの結果も修復済みの本文になる
- 修復した issue には label を付けて発動を観測できるようにする
- 変換と判定は scripts/ のスクリプトに隔離して単体テストを置く

routine 側の検証手順は残す。workflow と二重になるが、どちらが先でも結果は同じ本文になる。

## 結果

### 良くなったこと

- 壊れた issue が人手や LLM の自己修復に頼らず直る
- 今後 routine を追加しても対策を書き足す必要がない

### 引き受けたコスト

- 本文全体が壊れている issue では、inline code 内のリテラルな `\n` も実改行に変換される
- 1行に収まる健全な本文でも、inline code のリテラルな `\n` が閾値に届けば書き換わる。壊れた本文と見分ける手がかりが本文の中に無い

### 保留した論点

- 一部のセクションだけ `\n` で潰れた本文は検出されない。観測している壊れ方は全体が1行のものだけ
- リテラルの `\r\n` は実改行に戻さない。観測している壊れ方は `\n` だけなので、`\r` の2文字はそのまま残る
- 取りこぼしたときの日次 sweep は入れない
